## Hang captured under gdb (2026-10-25 23:02 – 2026-10-26 00:43, `hang_hunt.py`, `spec` FAST 500k, campaign flags, `-o /dev/null`)
Files: `bench-runs/hang-hunt/20261025T230242-spec-dna_fast_500k-{1,2}/`.
- **Run 1 completed:** `[main] Real time: 3990.994 sec`, 123 batches, accept rate α = 0.727, peak RAM 5.466 GB. Run under gdb with no power window, so it is **not** a measurement; indicative only (about −37 % against `upstream`'s 6,331 s at the same `-K`, in line with −37.5 % at 20k).
- **Run 2 hung** after 56 batches (2,009 s). At the hang: VDD_IN 6.08 W, GPU load node 999 ‰, 12 threads idle on futexes, and **one thread blocked in `cudaStreamSynchronize` called from `overlap_sync_repair_and_stitch` (`src/basecall.cpp:874`, via `basecall_chunks_overlap`, `pthread_single_basecall`)**, itself waiting in an `ioctl` to the Tegra host1x driver (`libnvrm_host1x.so`; kernel wait `dma_fence_default_wait`). So the host is waiting on the decode/repair stream's GPU fence and it never signals; the GPU is not doing work (6 W) but reports full load. `free -m` at the hang: 7,133 MB used, 236 MB available, swap 2,168 MB (the reduced-`-K` hang had only 5.9 GB used, so memory pressure is not required).
- **Superseded 2026-11-02** (the hang is inside the beam-search kernel, `exp/hang-root-cause.md`; kept as the record of what was suspected). **Candidate cause (hypothesis, untested):** a cross-stream lifetime race. Scores are produced on `infer_stream` (caching-allocator blocks belong to that stream) and consumed on `decode_stream` (`overlap_launch_decode` waits on `infer_event[slot]`, which orders the read after the write), but there is no `record_stream` anywhere in `basecall.cpp`. In the repair path, `hold->scores_NTC = hard_scores;` (≈ line 856) drops the original scores tensor right after queueing `index_select` on `decode_stream`; the allocator may hand that block to the next inference on `infer_stream` while the queued read has not run. A corrupted read on Tegra could fault the GPU channel (hang at idle power) instead of raising an error. The hangs in `ov_on`, `lb_baseline` and `cb_off` (no repair) would need the same rule applied to `pending->scores_NTC`. Cheap tests: keep the original tensor alive until the repair sync, and call `record_stream(decode_stream)` on scores consumed by the decode stream; then repeat `hang_hunt.py` (a 3-hour run without a hang would be ≈ 4 expected hangs avoided).

## Finding for the report: `upstream` → `ov_off` is −17.3 % (FAST 1k) / −19.6 % (FAST 20k) with overlap switched off (measured split 2026-10-30)
Larger than overlap's own step (−11.3 % / −14.5 %). The bundle run (below) splits it: **the whole gain appears at one commit, `e00bada` ("Enable stream-aware GPU decode for infer/decode overlap", overlap v1.0)**, which changes `src/basecall.cpp` (353 lines), `torchbox.cpp`, `CRFModel.cpp` and moves the openfish pin from `2530c2a` to the fork (`59e12e9`, 44 more openfish commits: 41 the maintainers', 3 Riley's). The instrumentation commits cost +3.2 % (FAST) and the later pinned-buffer commit (v1.1) changes nothing. **Measured against upstream's own current `dev` (`c2ca899`, openfish `991561a`): not faster than `upstream`** (FAST +0.2 % / −0.2 %, HAC +0.1 %; `--async=yes` −2.5 to −2.8 % FAST, −0.5 % HAC), so the maintainers' openfish development in `dev` does not by itself reproduce it. **Correction 2026-11-08:** `dev`'s openfish `991561a` branched from this lineage at `9b656e0` (2026-05-07) and does not contain BonsonW's June beam-search rewrite (`1f26d77`), which the fork pin since `e00bada` does contain; so the `dev` result does not rule out that rewrite as the source of the gain. What inside `e00bada` produces the gain (the slorado-side rewrite or the openfish update it needs) is still not separated: `e00bada` does not build with the old openfish pin, and its slorado side needs the new API.
